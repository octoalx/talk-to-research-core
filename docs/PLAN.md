# План реализации MVP для агента-кодера

**Статус:** 🟠 обсуждается (decisions/023, 024, 025 приняты)

Этот документ — задание для ИИ-агента, который пишет код ядра в
отдельном репозитории (decisions/004, 017). Он собран из `spec/01–06` и
решений 001–022 так, чтобы агент мог идти по шагам, не возвращаясь к
журналу. Если здесь что-то расходится с `spec/` или `decisions/`, верны
они, а этот план надо поправить.

## Что считаем MVP

MVP — **этап 1** из `spec/06-roadmap.md`: локальное ядро на Mac,
которое по документам `research/testset-by/` и правовым актам из пилота
отвечает со ссылками и проверенными цитатами, честно говорит «не нашёл» и
само прогоняет проверочный набор с отчётом.

**Входит:**
- загрузка своих документов (MD, DOCX, PDF с текстовым слоем) в одно рабочее пространство;
- загрузка актов права РБ из пилота скрейпингом pravo.by (decisions/022);
- деление на юридические единицы с адресами, гибридный поиск, reranker;
- ответ «утверждение + цитата», механическая проверка цитат (decisions/005);
- быстрый путь и режим «модель сама зовёт поиск» (decisions/021) с переключателем;
- прогон проверочного набора с отчётом по метрикам;
- минимальный веб-интерфейс в браузере (decisions/007);
- вопросы на русском и английском (decisions/014).

**Не входит** (следующие этапы): сканы и VLM-разборщик (идут отдельной
вехой M10 после основного MVP, когда в наборе появятся сканы, шаг 1a),
рукописное (decisions/019), слежение за папкой, извлечение фактов,
связи договор ↔ закон, редакции законов, агенты и MCP, Telegram-бот,
Tauri-приложение, несколько пространств.

## Как работать агенту (перенести в `AGENTS.md` кодового репозитория)

1. Идти по вехам M0 → M9 строго по порядку. Одна веха — одна ветка и
   один запрос на слияние; человек смотрит и сливает.
2. Веха готова, только когда выполнены все её проверки «Готово, когда»,
   прошли `make check` (линтер, типы, тесты) и, начиная с M5, прогон
   проверочного набора без ухудшения метрик прошлой вехи.
3. Сначала тест, потом код: для каждой вехи сначала пишутся тесты из
   раздела «Проверки», потом реализация.
4. Эталоны (`eval/`) не менять, чтобы тест прошёл. Если эталон кажется
   неверным, записать это в `docs/feedback.md` и спросить человека.
5. Версии библиотек и имена моделей из этого плана — на октябрь 2026 и
   могут устареть. Перед установкой проверить актуальные версии и
   записать выбранные в `docs/stack.md` с датой.
6. Если шаг упирается в неизвестное (разметка сайта, поведение модели),
   сделать минимальный замер, записать результат в `docs/results/` и
   выбрать вариант по умолчанию из плана. Не останавливаться молча.
7. Ничего не отправлять в сеть, кроме скачивания моделей, библиотек и
   актов с pravo.by. Документы пользователя не покидают компьютер.
8. Каждая функция ядра доступна из командной строки: так её можно
   проверить без интерфейса.
9. Связь с журналом (decisions/025): перед каждой вехой сравнить коммит
   журнала в `docs/journal.md` с текущим `main` журнала и перенести
   изменения `spec/12` и новых решений в `docs/PLAN.md`. Замеры писать в
   `docs/results/`, вопросы и расхождения с планом — в `docs/feedback.md`.
   В репозиторий журнала не писать.

## Исходные условия

- Железо разработки: MacBook Pro M4, 16 ГБ, macOS 26 (decisions/016).
- Язык: Python 3.12, менеджер `uv`, линтер `ruff`, типы `mypy` или
  `pyright`, тесты `pytest`.
- Сервер модели: Ollama, OpenAI-совместимый API, контекст задан явно
  (8 тыс.). Модель меняется только настройкой (decisions/003).
- Хранилище: один файл SQLite на пространство + отдельный файл пакета
  права, FTS5 + sqlite-vec, режим WAL (decisions/020).
- Проверочный набор: `research/testset-by/` из этого журнала копируется в
  кодовый репозиторий в `eval/testset-by/` один раз, дальше синхронизируется вручную.

## Структура репозитория

Предлагаемая раскладка (агент может уточнить, но не смешивать слои):

```
core/
  config        настройки (пути, модель, контекст, k поиска)
  llm           клиент OpenAI-совместимого API, потоковый вывод, вызов инструментов
  ingest        загрузка файла, хеш, версии
  parse         Docling → внутреннее представление, сохранение JSON разбора
  structure     деление на единицы, адреса, шапка контекста, проверка разбора
  law           скрейпер pravo.by и разбор актов
  normalize     ё→е, лемматизация (pymorphy3), токены для FTS5
  store         схема SQLite, миграции, паспорт индекса
  embed         эмбеддинги bge-m3, кэш по хешу текста
  search        FTS5, векторный поиск, RRF, точные адреса, reranker
  answer        промпт, структурированный ответ, проверка цитат
  chat          быстрый путь и агентный цикл с инструментами
  api           FastAPI: HTTP-эндпоинты и SSE для потокового ответа
cli/            команды: init, ingest, law fetch, index, search, ask, eval, bench
web/            минимальный интерфейс (HTML + немного JS, без сборщика)
eval/           testset-by, эталоны gold, сценарии замеров
docs/           stack.md, results/, notes.md
tests/
data/           (в .gitignore) пространства, пакеты права, сырьё скрейпинга
```

## Кто пишет код (decisions/026)

Основной исполнитель — Dark Factory Алекса (цель в Telegram → план →
одобрение → агент в песочнице → проверки → PR → merge делает Алекс).
На 2026-10-06 Factory умеет проверять только проекты на Node.js (npm);
поддержку Python нужно добавить в саму Factory, требования — в
`docs/factory.md` репозитория с кодом. До этого вехи M0–M1 делает
агент-кодер вне Factory (Claude Code или Codex) по тем же правилам.

Как резать вехи на цели Factory: одна цель — одна-две функции с тестами
(у агента 70 шагов, до 5 задач на цель). Замеры на Mac (M1, скорость
M5, итоговые прогоны M6–M9 с настоящей моделью) Factory готовит как
скрипты, а запускает Алекс на MacBook и кладёт отчёт в `docs/results/`.
Эталоны `eval/gold/` хранятся в Factory как скрытые сценарии (holdout).

## Вехи

### M0 — каркас репозитория

Сделать:
- `pyproject.toml`, `uv`, `ruff`, проверка типов, `pytest`, `Makefile` с `check`;
- файл настроек (`config.toml`) и загрузка настроек с переопределением через переменные окружения;
- копия `research/testset-by/` в `eval/testset-by/`;
- `AGENTS.md` из раздела «Как работать агенту»;
- `docs/stack.md` с проверенными версиями.

Проверить отдельно: Python, который ставит `uv`, разрешает загружать
расширения SQLite (`enable_load_extension`). Системный Python на macOS
этого не умеет (по документации sqlite-vec). Если не работает — взять
Python из Homebrew и записать это в `docs/stack.md`.

Для Dark Factory (decisions/026), чтобы проверки шли в песочнице без сети:
- зависимости зафиксированы в `uv.lock`;
- проверки запускаются без `uv run` и без доступа в сеть:
  `python -m ruff check .`, `python -m mypy core cli`, `python -m pytest -q
  -m "not mac and not model"` (pyright не брать: он скачивает Node при запуске);
- метки тестов: `mac` — нужен Mac (MLX, Metal), `model` — нужна настоящая
  модель (Ollama, bge-m3, reranker); всё остальное идёт везде;
- у клиента модели, эмбеддингов и reranker есть поддельные реализации
  для тестов (детерминированные ответы и векторы).

Готово, когда: `make check` проходит на пустом проекте; тест загружает
sqlite-vec и FTS5 в память и делает по одному запросу; те же три команды
проходят в чистом контейнере `python:3.12-slim` без сети после установки
зависимостей из `uv.lock`.

### M1 — модель и замер скорости (Q-04)

Сделать:
- клиент модели через OpenAI-совместимый API (Ollama), потоковый вывод,
  структурированный ответ по JSON-схеме, вызов инструментов;
- команда `bench`: для каждой модели из настроек измеряет время до
  первого токена, токены в секунду, пиковую память (по `ollama ps` и
  системе), на 3 типовых промптах длиной ~6 тыс. токенов;
- кандидаты: Qwen3.5 9B и Gemma 4 12B в 4 бит; запасной — Qwen3.5 4B
  (имена в библиотеке Ollama проверить, `research/local-models-2026.md`).

Готово, когда: отчёт `docs/results/M1-bench.md` с таблицей по моделям;
модель по умолчанию выбрана по правилу: быстрее при генерации не менее
10 токенов в секунду и помещается в память вместе с bge-m3. Качество
ответов сравнивается позже, на M7.

### M2 — загрузка и разбор документов

Сделать:
- загрузка файла: хеш содержимого, запись в `documents` и `versions`;
  тот же хеш — не разбирать заново, новый хеш — новая версия, старые
  единицы помечаются неактуальными;
- Docling: MD, DOCX, PDF с текстовым слоем → внутреннее представление;
  полный JSON разбора сохраняется рядом с исходником (decisions/020);
- тестовые PDF и DOCX: сделать из 12 договоров набора (pandoc или
  LibreOffice), положить в `eval/testset-by/contracts-pdf/` и `-docx/`.

Готово, когда: все 12 договоров в трёх форматах загружаются; текст после
разбора совпадает с исходным MD не менее чем на 98% (по символам после
нормализации пробелов); повторная загрузка того же файла ничего не меняет.

### M3 — деление на юридические единицы

Сделать по `spec/03-architecture.md` (модуль «Структура») и
`research/document-splitting.md`:
- деление по заголовкам и нумерации («1.», «2.3.», «Статья 15», «Глава 2»);
- адрес у каждой единицы («Договор № 14/26, п. 6.2»), родитель, страница;
- шапка контекста: название документа и путь разделов;
- без структуры — по абзацам 400–800 токенов с перекрытием;
- автопроверка разбора (мусорные символы, пустые страницы, разрывы
  нумерации, слишком длинные куски) с пометкой «разобран с ошибками»;
- команда, которая печатает дерево единиц документа.

Эталон: агент вручную составляет `eval/gold/units.yaml` — список адресов
пунктов для каждого из 12 договоров (например, у договора 01: 1.1, 2.1,
2.2, 3.1, 3.2, 4.1, 4.2, 5.1, 6.1, 6.2) и показывает его человеку до
реализации.

Готово, когда: адреса единиц совпадают с эталоном у всех 12 договоров во
всех трёх форматах; документ с перемешанной нумерацией получает пометку
«разобран с ошибками».

### M4 — правовые акты с pravo.by (decisions/022)

Сделать:
- сначала проверить `robots.txt` и условия pravo.by, вручную открыть
  2–3 акта и записать в `docs/notes.md`, как устроена страница;
- скрейпер по списку актов из `research/belarus-pilot.md`: ГК, Кодекс
  гражданского судопроизводства, Трудовой кодекс, Указ № 45 и Указ № 314,
  Закон № 126-З, постановление Совмина № 457;
- вежливый режим: не чаще одного запроса в 2–3 секунды, свой User-Agent,
  кэш сырья на диске; сырой HTML не меняется, разбор — отдельным шагом;
- деление актов: раздел → глава → статья → часть/пункт; адрес вида
  «ГК РБ, ст. 390, п. 1»; у каждой единицы адрес источника и дата загрузки;
- только действующие редакции;
- результат — отдельный файл пакета права (SQLite) с `index_meta`.

Если сайт не отдаёт тексты автоматически, запасной путь: человек сохраняет
страницы актов вручную в `data/raw/law/`, разбор работает с ними так же.

Готово, когда: все акты списка загружены; выборочно 20 случайных статей
сверены с сайтом (текст и номер совпадают); повторный запуск не качает
заново то, что уже есть.

### M5 — индекс (decisions/020)

Сделать:
- схема SQLite по `spec/05-data.md`, только таблицы этапа 1: collections,
  documents, versions, units, units_fts, unit_vectors, index_meta, queries;
- нормализация текста для поиска по словам: ё→е, нижний регистр,
  лемматизация pymorphy3 для русского, `porter` для английского; запрос
  нормализуется так же;
- эмбеддинги bge-m3 (через Ollama или sentence-transformers на MPS —
  выбрать по скорости), кэш векторов по хешу текста;
- паспорт индекса: модель эмбеддингов, размерность, версия схемы,
  лемматизатор; пакет права с другим паспортом не подключается (ATTACH);
- команда `index` для пространства и для пакета права.

Готово, когда: переиндексация без изменений не пересчитывает векторы;
поиск по слову «пени» находит пункты со словом «пеня»; пакет права с
чужим паспортом отклоняется с понятной ошибкой.

### M6 — поиск и замер поиска

Сделать:
- поиск по словам (FTS5, BM25) и по смыслу (sqlite-vec), объединение RRF;
- точный поиск адресов из вопроса («п. 6.2», «ст. 390», номер договора);
- фильтр по коллекции; reranker bge-reranker-v2-m3 оставляет 5–8 единиц;
- родитель–потомок: модель получает единицу вместе с её разделом;
- эталон `eval/gold/questions.yaml`: для каждого вопроса T-01…T-20 —
  список нужных адресов единиц (из столбца «Источник» в
  `questions.md`) и тип (📄, ⚖️, 🚫, сводный);
- 5–6 вопросов на английском (перевод части T-xx) с теми же эталонами;
- команда `eval --stage search`: доля вопросов, где все нужные единицы
  попали в топ-k, при k = 5 и 10, отдельно по типам.

Готово, когда: для обычных вопросов (одна-две нужные единицы) нужные
единицы в топ-5 не менее чем в 90% вопросов. Сводные вопросы (T-01,
T-04, T-06, T-11, T-12) в этот критерий не входят, их цифры пишутся
отдельно (decisions/024).

### M7 — ответ и проверка цитат (decisions/005)

Сделать:
- промпт с пронумерованными фрагментами; модель отвечает по JSON-схеме:
  список утверждений, у каждого — номер фрагмента и дословная цитата;
  либо явный признак «нет ответа»;
- проверка цитат: цитата ищется в тексте своего фрагмента после
  нормализации (пробелы, регистр, ё, кавычки, тире); утверждения без
  подтверждения удаляются; если ничего не осталось — «не нашёл в
  документах»;
- вывод: утверждения с адресами источников;
- журнал `queries`: вопрос, найденные единицы, ответ до и после
  проверки, путь, время до первого токена и полное время;
- команда `ask`.

Готово, когда: модульные тесты проверки цитат (подмена слова, лишняя
цифра, другой фрагмент) отбрасывают ложные цитаты; на T-17, T-18, T-19
ответ «не нашёл» или точное «в договоре не предусмотрено»; 100%
показанных цитат дословно есть в источниках.

### M8 — чат: быстрый путь и поиск по решению модели (decisions/021, Q-31)

Сделать:
- быстрый путь: выбрано пространство или документ, либо в вопросе явные
  признаки («мой договор», номер договора, имя контрагента) → поиск →
  ответ → проверка цитат;
- агентный путь: инструменты «искать в моих документах», «искать в
  праве», «открыть единицу по адресу»; не более 3 вызовов на вопрос;
  ответ без поиска помечается «в документах не искалось»;
- инструмент «пройти по всем документам пространства» (decisions/024):
  модель отвечает по каждому документу отдельно, ответы сводятся,
  каждое утверждение проходит проверку цитат; на быстром пути
  включается для сводных вопросов («какие договоры…», «во всех
  договорах…», «самая высокая…»);
- переключатель режима в настройках и в запросе;
- замер Q-31: `eval/gold/routing.yaml` — 40 сообщений (20 вопросов
  набора + 20 общих: «привет», «что такое неустойка», «переведи…») с
  ответом «искать / не искать»; команда `eval --stage routing`.

Правило по умолчанию: если модель верно решает «искать / не искать» не
менее чем в 90% сообщений и не ухудшает итоговые метрики M7, агентный
режим включён по умолчанию; иначе по умолчанию быстрый путь, а
агентный — по кнопке (decisions/021).

Готово, когда: отчёт `docs/results/M8-routing.md` с цифрами и выбранным
режимом.

### M9 — веб-интерфейс и полный прогон

Сделать:
- FastAPI: загрузка файлов, вопрос с потоковым ответом (SSE), просмотр
  источника по адресу;
- страница: поле вопроса, ответ по мере генерации, ссылки на источники,
  по клику — текст документа с подсвеченной единицей; переключатель
  режима; без React и сборщиков;
- поток: пока модель пишет, показывается ход работы («ищу», «нашёл 6
  фрагментов», «проверяю цитаты»), утверждения выводятся по мере
  проверки;
- команда `eval` (полный прогон): все метрики этапа 1 в
  `docs/results/eval-ГГГГ-ММ-ДД.md` плюс таблица для оценки человеком
  (вопрос, ответ, эталон, верно/неверно).

Готово (критерии этапа 1 из `spec/06-roadmap.md`):
- нужные единицы в топ-5 — не меньше 90% обычных вопросов;
- сводные вопросы — отдельная метрика: доля верных ответов по оценке
  человека и время ответа (decisions/024);
- 100% показанных цитат дословно есть в источниках;
- на вопросы 🚫 — «не нашёл» во всех случаях;
- верных ответов по оценке человека — не меньше 80%;

### M10 — сканы (после MVP, когда есть сканы в наборе)

## Что агенту не делать в MVP

- Не дообучать модели и не использовать LLM для деления документов (decisions/006, 018).
- Не подключать векторные серверы (Qdrant, Milvus) и PostgreSQL (decisions/020).
- Не использовать тяжёлые агентные фреймворки: свой цикл с фиксированными шагами (`spec/04-tech-stack.md`, Q-05).
- Не отправлять документы пользователя в облако.
- Не ставить сетевые сервисы наружу: API слушает только localhost.

## Риски плана (предположения, проверяются по ходу)

- pravo.by может не отдавать тексты автоматически или менять разметку →
  запасной путь с ручным сохранением страниц (M4).
- 9B-модель на 16 ГБ может не держать JSON-схему или вызов инструментов →
  структурированный вывод силами Ollama, запасная модель, быстрый путь
  по умолчанию (M7, M8).
- bge-m3, reranker и 9B вместе могут не поместиться в 16 ГБ → загружать
  reranker и эмбеддинги по очереди, выгружать после индексации
  (`spec/04-tech-stack.md`, бюджет памяти).
- Эталоны ⚖️ составлены по вторичным источникам → перед M9 сверить с
  текстами актов, загруженными на M4.
